# ۴. راهنمای Codex و Cursor

این فایل دستور کار عامل کدنویسی است. عامل باید پیش از هر تغییر آن را همراه سه سند قبلی بخواند.

## ۴.۱ مأموریت عامل

پروژه را فازبه‌فاز، با کمترین پیچیدگی لازم و تست‌های قابل تکرار بساز. هدف، تحویل MVP پایدار است؛ نه نمایش تعداد زیاد تکنولوژی‌ها.

## ۴.۲ قواعد اجباری

1. فقط فازی را پیاده‌سازی کن که کاربر صراحتاً درخواست کرده است.
2. قبل از تغییر، وضعیت Git و فایل‌های موجود را بررسی کن.
3. تغییرات نامرتبط کاربر را حفظ کن.
4. ابتدا interface و schema، سپس implementation را بساز.
5. هر رفتار مهم باید تست داشته باشد.
6. تست‌های عادی نباید به اینترنت وابسته باشند.
7. هیچ secret یا `.env` واقعی را commit نکن.
8. از SDK رسمی `google-genai` استفاده کن.
9. از `google-generativeai` قدیمی استفاده نکن.
10. provider فعال فقط `GeminiProvider` است.
11. نام مدل Gemini را hard-code نکن؛ از settings بخوان.
12. structured output را با Pydantic schema اعتبارسنجی کن.
13. مدل را منبع حقیقت برای URL، تاریخ یا ادعاهای بیرونی قرار نده.
14. scheduler را داخل process وب اجرا نکن.
15. تا قبل از نیاز واقعی، Redis، Celery، React، Docker و vector database اضافه نکن.

## ۴.۳ تصمیم‌گیری هنگام ابهام

عامل می‌تواند تصمیم‌های کوچک و برگشت‌پذیر را با این اولویت بگیرد:

1. ساده‌ترین راهی که معیار پذیرش را برآورده کند.
2. راهی که تست offline را آسان کند.
3. راهی که مرز domain و infrastructure را حفظ کند.
4. راهی که انتقال SQLite به PostgreSQL را سخت نکند.

اگر تصمیم روی scope، هزینه API، داده کاربر، امنیت یا رفتار محصول اثر معنادار دارد، پیش از اجرا از کاربر سؤال شود.

## ۴.۴ سیاست dependency

قبل از افزودن package جدید:

- بررسی کن کتابخانه موجود همان نیاز را حل نمی‌کند.
- package فعال و سازگار با نسخه Python پروژه باشد.
- دلیل آن در توضیح تغییر ذکر شود.
- dependencyها version range معقول داشته باشند.

وابستگی‌های مورد انتظار:

- fastapi
- uvicorn
- sqlalchemy
- alembic
- pydantic
- pydantic-settings
- httpx
- feedparser
- trafilatura
- beautifulsoup4
- google-genai
- rapidfuzz
- jinja2
- pytest و ابزارهای async موردنیاز تست

همه این موارد نباید در فاز صفر یک‌جا نصب شوند؛ هر package در اولین فازی که نیاز است اضافه شود.

## ۴.۵ قرارداد کیفیت کد

- Python type hint برای APIهای داخلی اجباری است.
- توابع domain تا حد امکان pure باشند.
- session دیتابیس lifespan مشخص داشته باشد.
- transaction boundary در service/repository روشن باشد.
- exceptionهای infrastructure به exceptionهای معنادار داخلی تبدیل شوند.
- از `except Exception: pass` استفاده نشود.
- logها structured و بدون متن کامل مقاله یا secret باشند.
- timezone-naive datetime وارد دیتابیس نشود.
- enumها در یک محل مرکزی تعریف شوند.
- magic numberها به settings یا constant نام‌دار منتقل شوند.

## ۴.۶ سیاست Gemini

### انتخاب مدل

مقدار نمونه فعلی:

```env
GEMINI_MODEL=gemini-3.5-flash-lite
```

این مقدار قرارداد دائمی نیست. عامل هنگام راه‌اندازی واقعی باید از Google AI Studio یا مستندات رسمی بررسی کند که:

- مدل در حساب کاربر فعال است.
- Free Tier دارد یا با سیاست هزینه کاربر سازگار است.
- structured output را پشتیبانی می‌کند.
- quota برای حجم MVP کافی است.

### رفتار provider

- client با API key از environment ساخته شود.
- مدل فقط متن مقاله دریافت کند.
- Google Search grounding در MVP غیرفعال باشد.
- response schema صریح باشد.
- response پس از دریافت دوباره با Pydantic validate شود.
- usage metadata در صورت ارائه SDK ثبت شود، اما نبود آن خطا نیست.
- خطاها sanitize شوند.

### تست provider

- تست اصلی با fake client یا fake provider.
- تست contract تضمین کند request درست و schema معتبر است.
- تست live marker جدا داشته باشد.
- تست live خودکار یا پیش‌فرض اجرا نشود.

## ۴.۷ سیاست migration

- schema با Alembic تغییر کند.
- `create_all` جای migration را در اجرای واقعی نگیرد.
- هر migration هم upgrade و هم downgrade معقول داشته باشد.
- migration destructive بدون تأیید کاربر انجام نشود.
- migration روی دیتابیس خالی در تست اجرا شود.

## ۴.۸ سیاست HTTP و scraping

- robots.txt و شرایط منبع رعایت شود.
- rate limit محافظه‌کارانه باشد.
- timeout اجباری.
- retry فقط برای خطای موقت.
- header User-Agent مشخص.
- paywall/CAPTCHA دور زده نشود.
- صفحه خراب به‌عنوان خطای یک article ثبت شود، نه failure کل run.
- adapter اختصاصی سایت فقط وقتی ساخته شود که extractor عمومی کافی نباشد.

## ۴.۹ Definition of Done هر فاز

یک فاز فقط وقتی کامل است که:

- تمام معیارهای پذیرش سند roadmap برآورده شده باشد.
- تست مرتبط اضافه و اجرا شده باشد.
- lint/type check تعریف‌شده پروژه پاس شود.
- migration لازم ایجاد و آزمایش شده باشد.
- README یا مستند مربوط در صورت تغییر رفتار به‌روز شده باشد.
- هیچ secret یا فایل موقت وارد Git نشده باشد.
- عامل محدودیت‌ها و کارهای باقی‌مانده را شفاف گزارش کند.

## ۴.۱۰ قالب گزارش پایان فاز

عامل در پایان هر فاز این قالب را استفاده کند:

```text
نتیجه فاز:
- خروجی اصلی

تغییرات:
- فایل‌ها و قابلیت‌های مهم

اعتبارسنجی:
- دستورها و نتیجه تست‌ها

تصمیم‌های گرفته‌شده:
- تصمیم‌هایی که در مستند صریح نبودند

محدودیت‌ها:
- موارد شناخته‌شده یا موکول‌شده

آماده برای:
- نام فاز بعدی، بدون شروع خودکار آن
```

## ۴.۱۱ prompt آماده برای شروع با Codex یا Cursor

متن زیر را می‌توان برای شروع هر فاز استفاده کرد:

```text
تمام فایل‌های README.md و docs/01 تا docs/04 را کامل بخوان. سپس فقط فاز [شماره فاز] از docs/03-implementation-roadmap.md را اجرا کن. پیش از ویرایش، وضعیت repository و کد موجود را بررسی کن. از تصمیم‌های معماری مستند پیروی کن، تست‌های همان فاز را اضافه و اجرا کن و وارد فاز بعد نشو. اگر بین کد موجود و مستند تعارضی دیدی یا تصمیمی روی scope، امنیت یا هزینه API اثر معنادار دارد، قبل از اجرا آن را مطرح کن. در پایان، گزارش را مطابق قالب docs/04-coding-agent-guide.md ارائه بده.
```
