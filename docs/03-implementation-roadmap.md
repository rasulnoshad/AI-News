# ۳. برنامه پیاده‌سازی مرحله‌به‌مرحله

## قواعد عمومی اجرای roadmap

- هر فاز یک branch/commit مستقل داشته باشد، مگر کاربر روش دیگری بخواهد.
- قبل از شروع هر فاز، scope و فایل‌های مرتبط مرور شوند.
- بعد از هر فاز، تست‌ها اجرا و نتیجه گزارش شود.
- وابستگی یا قابلیت متعلق به فاز بعدی زودتر اضافه نشود.
- برای تصمیم مبهم، ابتدا مستندات به‌روزرسانی سپس کد نوشته شود.

## فاز ۰: اسکلت و ابزارهای پایه

### هدف

ایجاد پروژه‌ای که نصب، اجرا و تست می‌شود، ولی هنوز خبر دریافت نمی‌کند.

### وظایف

1. ساخت packageهای اصلی بر اساس معماری.
2. تعریف dependency management؛ پیشنهاد: `pyproject.toml` با uv یا pip-compatible configuration.
3. افزودن FastAPI، Uvicorn، SQLAlchemy، Alembic، Pydantic Settings و pytest.
4. ایجاد `Settings` و `.env.example`.
5. ایجاد logging ساختاریافته پایه.
6. ایجاد endpointهای `/health/live` و `/health/ready`.
7. ایجاد دیتابیس و migration اولیه.
8. ایجاد `.gitignore`.
9. ایجاد commandهای استاندارد در README توسعه.

### معیار پذیرش

- برنامه روی `127.0.0.1` اجرا شود.
- `/health/live` پاسخ ۲۰۰ دهد.
- migration روی دیتابیس خالی اجرا شود.
- تست‌ها بدون اینترنت سبز باشند.
- نبود `GEMINI_API_KEY` مانع health endpoint نشود.

### توقف فاز

عامل پس از تحقق معیارها گزارش می‌دهد و بدون تأیید کاربر وارد فاز بعد نمی‌شود.

## فاز ۱: دیتابیس و registry منابع

### هدف

تعریف مدل‌های داده و ثبت سه منبع اولیه.

### وظایف

1. پیاده‌سازی enumها و مدل‌های SQLAlchemy.
2. migration جدول‌های MVP.
3. repositoryهای موردنیاز pipeline.
4. seed idempotent سه منبع اولیه.
5. تست constraintها و seed دوباره.

### معیار پذیرش

- تمام جدول‌های مستند ایجاد شوند.
- اجرای چندباره seed رکورد تکراری نسازد.
- `canonical_url` unique باشد.
- زمان‌ها timezone-aware و UTC باشند.
- سه منبع از دیتابیس قابل خواندن باشند.

## فاز ۲: RSS discovery

### هدف

دریافت Feed و ذخیره مقالات جدید، بدون استخراج صفحه.

### وظایف

1. تعریف `FeedClient` و DTOها.
2. پیاده‌سازی دریافت با httpx و parse با feedparser.
3. canonicalization URL.
4. پردازش تاریخ‌های Feed و fallback امن.
5. ذخیره idempotent مقالات.
6. به‌روزرسانی وضعیت منبع.
7. command مانند `python -m app.cli discover`.
8. fixture برای حداقل دو نوع RSS/Atom.

### معیار پذیرش

- fixtureها parse شوند.
- اجرای دوباره روی fixture مقاله تکراری نسازد.
- خرابی یک منبع، نتیجه دیگر منابع را حفظ کند.
- timeout و User-Agent وجود داشته باشد.
- summary اجرا تعداد discovered/new/errors را نشان دهد.

## فاز ۳: استخراج محتوای مقاله

### هدف

تبدیل URL مقاله به متن تمیز و metadata قابل استفاده.

### وظایف

1. تعریف interface استخراج.
2. پیاده‌سازی trafilatura.
3. fallback metadata با BeautifulSoup/JSON-LD.
4. hash متن normalize‌شده.
5. کنترل حداقل طول.
6. وضعیت و خطاهای مرحله‌ای.
7. fixtureهای HTML شامل مقاله خوب، صفحه خراب و متن کوتاه.

### معیار پذیرش

- عنوان و متن fixture معتبر استخراج شوند.
- منو و navigation وارد متن اصلی نشوند.
- صفحه کوتاه/نامعتبر شکست کنترل‌شده ایجاد کند.
- HTML خام و secret وارد log نشوند.
- اجرای مجدد مقاله موفق بی‌دلیل fetch جدید انجام ندهد، مگر force شود.

## فاز ۴: GeminiProvider و تحلیل ساختاریافته

### هدف

تحلیل مقاله با Gemini API و ذخیره خروجی معتبر فارسی.

### وظایف

1. افزودن dependency رسمی `google-genai`.
2. تعریف `LLMProvider` protocol.
3. تعریف Pydantic request/result schema.
4. نوشتن prompt نسخه `v1`.
5. پیاده‌سازی `GeminiProvider` با model از settings.
6. فعال‌کردن structured output با JSON schema.
7. محدودکردن اندازه ورودی.
8. مدیریت خطاهای 429، 5xx، timeout، 400 و 403.
9. ذخیره model، prompt version و نتیجه.
10. ساخت `FakeLLMProvider` برای تست.
11. افزودن یک تست زنده اختیاری.

### معیار پذیرش

- تمام unit/integration testها بدون API key اجرا شوند.
- Fake provider خروجی pipeline را کامل کند.
- خروجی نامعتبر قبل از دیتابیس رد شود.
- API key در هیچ log یا exception نمایشی نباشد.
- مقاله تحلیل‌شده با hash/model/prompt یکسان دوباره درخواست نشود.
- تست زنده اختیاری، در صورت وجود کلید و دسترسی، یک پاسخ فارسی schema-valid بگیرد.

### نکته تصمیم‌گیری مدل

مدل پیش‌فرض از environment انتخاب شود. هنگام اجرای واقعی، عامل باید مدل رایگان فعال و پشتیبان structured output را در حساب Google AI Studio تأیید کند. تغییر مدل نباید تغییر کد نیاز داشته باشد.

## فاز ۵: گروه‌بندی رویدادهای مشابه

### هدف

تبدیل چند مقاله درباره یک اتفاق به یک رویداد خبری.

### وظایف

1. dedup دقیق با URL و content hash.
2. normalize عنوان.
3. شباهت عنوان با RapidFuzz.
4. استفاده از entity و event key termهای Gemini.
5. محدودکردن مقایسه به پنجره زمانی مناسب، مثلاً ۷۲ ساعت.
6. انتخاب مقاله اصلی طبق قواعد.
7. حفظ لینک تمام مقالات.

### معیار پذیرش

- fixture سه مقاله درباره یک اتفاق را یک رویداد کند.
- دو خبر متفاوت از یک شرکت را اشتباه ادغام نکند.
- منبع رسمی به‌عنوان primary انتخاب شود.
- هر مقاله حداکثر به یک event فعال متعلق باشد.

## فاز ۶: امتیازدهی و digest

### هدف

ساخت گزارش روزانه محدود و مرتب.

### وظایف

1. پیاده‌سازی component scoreها.
2. پیاده‌سازی فرمول deterministic.
3. محاسبه coverage بر اساس تعداد منبع مستقل.
4. اعمال بازه ۲۴ ساعته بر اساس timezone.
5. انتخاب حداکثر `DAILY_DIGEST_LIMIT` رویداد.
6. ذخیره snapshot امتیاز و ترتیب.
7. بازسازی idempotent digest همان روز.

### معیار پذیرش

- limit رعایت شود.
- ترتیب با score نزولی باشد.
- اجرای دوباره آیتم تکراری نسازد.
- مرز روز تهران با زمان UTC درست تست شود.
- خبر رسمی مهم با یک منبع به شکل مصنوعی حذف نشود.

## فاز ۷: pipeline end-to-end و CLI

### هدف

یک command تمام مراحل را با isolation خطا اجرا کند.

### وظایف

1. runner مرحله‌ای.
2. ثبت `pipeline_runs` و شمارنده‌ها.
3. جلوگیری از اجرای هم‌زمان.
4. گزینه‌های `--source`, `--force`, `--since`, `--skip-llm` در حد نیاز.
5. exit code مناسب برای success، partial و failure.
6. integration test کامل با fakeها.

### معیار پذیرش

- یک command از fixture تا digest را کامل کند.
- خطای یک article ادامه run را متوقف نکند.
- وضعیت run در حالت موفق، جزئی و شکست درست باشد.
- lock اجرای هم‌زمان را متوقف کند.

- لینک اصلی در تب جدید باز شود.

## فاز ۱۰: آماده‌سازی انتقال به سرور

این فاز جزو تحویل MVP محلی نیست، اما معماری باید مانع آن نشود.

- scheduler جدا از web process

- backup و retention
- secret management

## ترتیب پیشنهادی تعامل با عامل کدنویس

برای هر فاز:

1. کاربر می‌گوید: «فاز N را طبق مستندات اجرا کن.»
2. عامل تمام فایل‌های مستند را می‌خواند.
3. عامل وضعیت repository را بررسی می‌کند.
4. فقط plan همان فاز را اعلام می‌کند.
5. کد و migration و تست همان فاز را می‌سازد.
6. تست‌ها را اجرا می‌کند.
7. اختلاف احتمالی با مستند را گزارش می‌کند.
8. نتیجه و فایل‌های مهم را تحویل می‌دهد.
9. منتظر تأیید برای فاز بعد می‌ماند.
